## Problemas que encontraron y cómo los diagnosticaron

1. **Error tipográfico en la imagen base de `orders/Dockerfile` (`node:20-alpne`):**
   - **Diagnóstico:** Al revisar `orders/Dockerfile` y ejecutar `docker compose build orders`, Docker falló inmediatamente con el mensaje de error: `ERROR: failed to solve: node:20-alpne: failed to resolve source metadata for docker.io/library/node:20-alpne: pull access denied, repository does not exist or may require 'docker login': manifest for node:20-alpne not found`.
   - **Solución:** Se corrigió el tag a `alpine` (actualizado luego a `FROM node:22-alpine` en el Incidente 2) y se reestructuró en dos etapas (`deps` y `runner`) con usuario `node` y `HEALTHCHECK`.

2. **Fuga de secretos, ejecución como `root` y compiladores pesados en `catalog/Dockerfile`:**
   - **Diagnóstico:** Al ejecutar `python tools/verify.py --static` (`catalog/Dockerfile tiene 1 FROM; falta .dockerignore`) e inspeccionar `catalog/Dockerfile`, detectamos que tenía `ENV POSTGRES_PASSWORD=<secreto_expuesto>` hardcodeado en una capa de la imagen, instalaba `gcc` y `libpq-dev` en la misma etapa final sobre `python:3.12` (>1 GB) y copiaba todo el código (`COPY . /app`) antes de `pip install -r requirements.txt` (invalidando la caché de capas en cada cambio de código).
   - **Solución:** Se eliminó `ENV POSTGRES_PASSWORD`, se implementó un multi-stage build con Python Alpine y `/opt/venv`, se copió `requirements.txt` antes del código, se añadió `libpq` y el usuario sin privilegios `10001:10001`, y se crearon los `.dockerignore` de los 4 servicios.

3. **Inicialización y orden de arranque de la base de datos y servicios de backend:**
   - **Diagnóstico:** Al revisar el esqueleto inicial de `docker-compose.yml` con `docker compose config`, observamos que `db` no montaba `./db/init.sql` en `/docker-entrypoint-initdb.d/` ni tenía `healthcheck`, por lo que `catalog`, `orders` y `worker` arrancaban antes de que PostgreSQL estuviera listo para aceptar conexiones.
   - **Solución:** Se configuraron los healthchecks de `db` y `cache` y se añadió `depends_on` con `condition: service_healthy` en `catalog`, `orders`, `worker` y `frontend`.

4. **La política `restart` no revive a Redis después de un `docker compose kill -s SIGKILL cache` (Incidente 3):**
   - **Diagnóstico:** Al ejecutar `python incident3.py`, respondía `Redis no volvió a estar en pie en 60s` aunque `cache` ya tenía `restart: unless-stopped`. Con `docker inspect -f '{{.HostConfig.RestartPolicy.Name}} {{.RestartCount}}' equipo07-cache-1` vimos `restarts=0`. Probamos `always`, `unless-stopped` y `on-failure`: las tres reinician si el proceso interno de Redis muere solo, pero ninguna después de `docker compose kill`, porque el daemon de Docker (29.x) marca la detención vía API (`kill`) como parada intencional del usuario y desactiva el auto-restart.
   - **Solución:** Se implementó el servicio `cache-guard` (`docker:27-cli`) que vigila los contenedores del proyecto con etiqueta `com.docker.compose.service=cache` en estado `exited` y los levanta con `docker start`. Para mitigar el riesgo de montar `/var/run/docker.sock`, corre con `network_mode: none`, `read_only: true`, `cap_drop: [ALL]` y `no-new-privileges:true`.

## Uso de IA

Utilizamos un asistente de IA como apoyo para analizar la rúbrica de `tools/verify.py`, estructurar los multi-stage builds, diagnosticar el comportamiento de `docker kill` en el Incidente 3 y revisar la sintaxis de los healthchecks. Tuvimos que verificar y corregir cuatro puntos clave respecto a sugerencias iniciales:
1. En las imágenes Python basadas en Alpine (`catalog` y `worker`), añadimos explícitamente `apk add --no-cache libpq` en la etapa final y `--chown=10001:10001` para evitar errores de librerías dinámicas y permisos con el usuario no-root.
2. En `catalog/.dockerignore` y `worker/.dockerignore`, corregimos un error tipográfico (`__pycache_` -> `__pycache__/`) para excluir efectivamente la caché de bytecode de Python.
3. Ajustamos el orden de instrucciones `COPY` en `orders/Dockerfile` y `catalog/Dockerfile` para que el test automático de caché (`check_cache`) no reinstale dependencias al editar `server.js` o `main.py`.
4. En el Incidente 3, la sugerencia estándar de cambiar `cache` a `restart: always` fue probada y descartada porque el daemon de Docker inhibe el restart policy cuando la señal `SIGKILL` proviene del comando `docker kill`; en su lugar diseñamos el sidecar `cache-guard` endurecido (`network_mode: none`, `cap_drop: ALL`, `read_only: true`).

## Qué haríamos distinto con más tiempo

1. **Gestión de secretos con Docker Secrets:** En lugar de pasar contraseñas por variables de entorno desde `.env`, montaríamos archivos en `/run/secrets/postgres_password` (adaptando las aplicaciones para leer `POSTGRES_PASSWORD_FILE`).
2. **Aislamiento de red aún más estricto:** Separaríamos la red interna en dos redes con `internal: true` (`db-net` y `redis-net`) para que `catalog` no tenga visibilidad de red hacia Redis y ningún servicio de datos sea alcanzable por servicios que no lo consumen.
3. **Fijación de versiones por digest SHA256 y escaneo continuo de vulnerabilidades:** Fijaríamos los digests inmutables de las imágenes base (`python:3.13-alpine@sha256:...`, `node:22-alpine@sha256:...`) e integraríamos `docker scout` o `trivy` en un pipeline de CI (GitHub Actions) antes de cada merge a `main`.
